2 · Chip to token

What happens when you send a prompt

One request, followed through the hardware. The two phases stress different parts of the chip, and that split explains most hardware design choices today.

STEP 1

Tokenize

Text becomes a list of integer IDs, roughly ¾ of a word each.

STEP 2

Prefill

All prompt tokens run through every layer at once. Huge matrix multiplies.

compute-bound
STEP 3

KV cache

Each layer saves keys and values for every token so they aren't recomputed. It grows with context length.

fills memory
STEP 4

Decode

One new token at a time. Each step re-reads all the weights plus the KV cache from HBM.

memory-bound
STEP 5

Batch

Serve many users per weight read to share the cost. More users per GPU means cheaper tokens but slower tokens for each.

throughput vs latency

The core idea. During decode, the chip spends most of its time waiting for bytes, not doing math. A GPU can do hundreds of multiplies for every byte it can fetch from HBM. That is why memory bandwidth, KV cache size and batching dominate inference economics, and why HBM makers and packaging became kingmakers.

4 · Players

Who owns which layer, and why it's hard to displace them

NVIDIA

Designs GPUs, NVLink, networking, and full racks (GB200/GB300 NVL72). Fabless: TSMC makes the chips.

Moat: CUDA software ecosystem plus selling a whole system, not a chip.

TSMC

Manufactures leading-edge chips for NVIDIA, AMD, Apple, Google, AWS. Also runs CoWoS packaging.

Moat: decades of process yield know-how. Almost no second source at the frontier.

ASML

Only maker of EUV lithography machines, each costing well over $150M.

Moat: a supply chain of its own (Zeiss optics) that took 20+ years to build.

SK hynix, Samsung, Micron

The three HBM makers. HBM uses far more wafer per bit than normal DRAM.

Moat: stacking yield. SK hynix has led on NVIDIA supply.

Hyperscalers

Google (TPU), Amazon (Trainium), Microsoft (Maia), Meta (MTIA) build custom chips, often with Broadcom or Marvell.

Why: avoid NVIDIA's margins for workloads they fully control.

Challengers

AMD (MI300/MI350 series) is the main merchant GPU alternative. Cerebras and Groq use very different chip designs.

Hurdle: software maturity and rack-scale systems, more than raw FLOPS.

7 · Deep dive 1

Inside the model, the GPU and its memory

Goal: by the end of this section you can redo the math in the GPU package diagram and explain the shape of the two batching charts yourself. Read the six parts in order; each one builds on the last.

7.1A model is a big pile of numbers

A trained model is a list of numbers called weights (or parameters). A "70B" model has 70 billion of them. Running the model means multiplying your input against those numbers. Nothing else is stored in the model: no text, no database, just weights.

How much memory that takes depends on how many bytes each number uses, which is the precision. FP16 uses 2 bytes per number, FP8 uses 1, FP4 uses half a byte. Fewer bytes means a smaller model, less data to move, and faster math, at some cost in accuracy. Newer chips add hardware for lower precisions: Hopper (H100) added FP8, Blackwell (B200) added FP4.

Model size in bytes = parameters × bytes per parameter. That is step 1 of the package math.

7.2How a transformer makes one token

Text is split into tokens (word pieces). Each token becomes a vector: a list of a few thousand numbers (8,192 for a 70B-class model) that the model can do math on. That vector then passes through a stack of identical layers, 80 of them in a 70B model. Each layer has two parts:

Attention lets the current token look back at every earlier token in the conversation and pull in what's relevant. This is how "it" knows which noun it refers to. MLP (the feed-forward block) then transforms the vector using most of the model's weights. This is where most of the model's stored knowledge acts.

After the last layer, the model outputs a score for every token in its vocabulary. One is picked, appended to the text, and the whole stack runs again for the next token. Generating a 500-token answer means running all 80 layers 500 times, one after another.

Prefill vs decode, again. When your prompt first arrives, all its tokens go through the layers together in one big pass (prefill). After that, the model is stuck producing one token per trip around the loop (decode), because each new token depends on the one before it.

7.3The KV cache: the model's short-term memory

For attention to "look back", each earlier token needs to be represented in every layer by two vectors, a key (what this token is about) and a value (what it contributes). Recomputing these for the whole conversation on every step would be wasteful, so they are computed once and stored in HBM. That store is the KV cache.

It belongs to one conversation, it grows by one entry per token, and it must be read in full on every decode step. For a Llama-70B-style model the size per token works out like this:

aK and V, per layer2 b× layers× 80 c× KV heads × numbers per head× 8 × 128 d× bytes per number (FP16)× 2 ≈ 0.33 MB per token. A 4,000-token conversation ≈ 1.3 GB. A 100,000-token one ≈ 33 GB.

Weights are shared by every user. The KV cache is per user. That difference drives the batching charts.

7.4The one operation that matters: multiply-add

Almost all the work in a transformer is multiplying a vector by a weight matrix. Each weight gets used for exactly one multiply and one add per token. So a rule of thumb: one token costs about 2 × parameters in math, or 140 billion operations (GFLOP) for a 70B model.

The catch is that each weight has to travel from HBM to the compute cores before it can be used. With one user, a weight makes that trip to be used just once. With many users batched together, the vector becomes a matrix (one column per user) and the same weight, fetched once, is reused for every user.

7.5Inside the GPU: a memory hierarchy

A GPU is thousands of small multiply-add units (tensor cores) grouped into blocks called SMs (streaming multiprocessors; an H100 has 132). They are fed by a ladder of memories. Each step closer to the cores is faster but much smaller.

Gold bar = relative speed, not to scale.

SRAM vs DRAM vs HBM. SRAM stores each bit in about six transistors built right into the logic chip. It's very fast and needs no refresh, but it takes lots of area, so there is only a little of it. DRAM stores each bit as charge in a tiny capacitor with one transistor. It's dense and cheap, but slower, and it lives on separate memory chips. HBM is DRAM with a different shape: 8 to 12 DRAM dies stacked vertically, joined by thousands of vertical wires, and placed a few millimetres from the GPU. A regular server memory channel is 64 bits wide. An HBM stack is 1,024 bits wide, so it moves far more bytes per second. That width is why it needs the interposer from the package diagram.

A model's weights (tens of GB) can't fit in SRAM (tens of MB), so every decode step streams them from HBM. HBM bandwidth is the speed limit.

7.6Putting it together: the roofline, the package math, the charts

Every chip has two limits: how fast it can do math, and how fast it can move bytes. Divide one by the other and you get the chip's balance point. A B200 does about 4,500 trillion FP8 operations per second and moves 8 TB/s, so it needs roughly 560 operations per byte to keep its math units busy. Below that, the chip is waiting on memory. The roofline chart shows this: a sloped roof where memory limits you, and a flat roof where math does.

The GPU package math, step by step. One user, 70B model at FP8 on one B200:

1Weights to read each step (7.1)70B × 1 B = 70 GB 2Time to stream them from HBM70 GB ÷ 8,000 GB/s ≈ 8.75 ms 3Math needed for one token (7.4)2 × 70B = 140 GFLOP 4Time to do that math140 GFLOP ÷ 4,500 TFLOP/s ≈ 0.03 ms 5The slower of the two sets the pace≈ 8.75 ms per step 1 ÷ 8.75 ms ≈ 114 steps a second, one token each, so about 110 tokens/s for a single user. The math units are idle about 99.7% of the time.

Going from 1 to 8 users barely slows anyone down, because the weights dominate the bytes and they're shared. After that, each new user adds 1.3 GB of KV cache to every step, so everyone slows down. At about 90 users, 187 GB of the 192 GB is used and nobody else fits. That is the whole throughput vs latency tradeoff, and it all falls out of one division: bytes ÷ bandwidth.

This is why the industry cares so much about HBM bandwidth and capacity, lower precisions like FP8 and FP4 (fewer bytes), and tricks that shrink the KV cache. Each one moves a number in this table.
